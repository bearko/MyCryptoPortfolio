## 1. 決めること

SPEC-001 8 章のルールに沿って、**タイトルごとの計算式と基準プレイ** を決める。

- 総合スコア ＝ 各タイトルの **自己ベストのタイトルスコアの合計**
- 計算式に入れるのは **そのプレイの成績だけ**。初回クリア・順位は入れない（D5）
- **上限は設けない**（D11）。基準 B は「ふつうに遊んでクリアしたときの目安」で、イベントの上振れや研究でハイスコアが更新され続けるようにする
- **計算式で頭打ち・段差を作らない**。ステージクリアなどの節目には決まった点を入れ、それ以外の成績はゲーム内の成績に係数を掛けるだけにする

## 2. 共通の形：節目の点 ＋ 成績の点

| 部分 | 何で決まるか | 点 |
|---|---|---|
| **節目の点** | ステージ・章・レベル・ノードのクリアなど、ゲーム内の節目 | 節目ごとに **決まった点**。最初の節目 ＝ **1,000**（基準 A）、ゲームクリア ＝ **5,000** |
| **成績の点** | ゲーム内のスコアや、純資産・タイムなどの成績 | 成績 × **係数**。上限なし。ふつうにクリアしたプレイで **約 5,000**（→ 合計 約 10,000 ＝ 基準 B）になるように係数を決める |

- 係数は「ふつうにクリアしたプレイの成績」から逆算する（例：ふつうのクリアでゲーム内スコアが 20,000 なら、係数は 5,000 ÷ 20,000 ＝ 0.25）
- 成績の点は、**その成績が良くなるほど、同じ割合で増え続ける**。上限・頭打ち・途中で係数が変わる区切りは作らない
- 難易度・レギュレーションの倍率は、ゲーム内スコアに入っていれば、そのまま効く（節目の点には掛けない。難しい設定で 1 面だけ遊ぶのが得にならないように）
- ゲームのバランスを変えて「ふつうのクリア」の成績が変わったら、**係数だけ** を直す（計算式の版を上げて、保存してある生の成績から全員を計算し直す。SPEC-001 8.4）

> 気をつけること：上限がないので、あるタイトルの成績が大きく伸びやすいと、総合がそのタイトルで決まりやすくなる。そうなったら上限ではなく係数で合わせる（作者が点数の分布を見て判断する）。

## 3. タイトルごとの計算式

太字の数字は **暫定値**（作者の決定 2026-10-16：この基準で実装を進める）。遊ばれた成績を見て、係数だけを直す。

### 3.1 Tactics（1 プレイ ＝ 1 回の挑戦）

| | 中身 |
|---|---|
| 節目の点 | クリアした章 × 1,000（第 1 章 1,000 〜 全 5 章 5,000）。難易度の係数は掛けない |
| 成績の点 | 全章クリアのとき：**倍率の前の点** × **難易度の係数** × **0.25** |
| 倍率の前の点 | ゲーム内の最終スコアから、レギュレーション倍率と ABSOLUTE の倍率を除いた点（ターン数・デッキ枚数・LL・レアリティ。Tactics の `scoreBreakdown.baseScore`） |
| 難易度の係数 | 共通基盤で決める（作者の決定 2026-10-17）：Common **1.0** ／ Dragon Egg **1.2** ／ Baby Dragon **1.4** ／ Blue Dragon **1.7** ／ Red Dragon **2.0** ／ ABSOLUTE は **ABSOLUTE の倍率そのもの、ただし Red（2.0）を超えない**（下限はない。やさしい設定ほど小さい） |
| 係数の根拠 | ふつうのクリアの倍率の前の点を **20,000** と見た（SPEC-007 の例「100 ターン・20 枚・Common 3 体」＝ 20,500） |
| 例 | 第 1 章まで 1,000 ／ Common でふつうに全章クリア 10,000 ／ Red で同じ内容 15,000 ／ ABSOLUTE（倍率 2,500）でも 15,000 |
| 送る成績 | `chaptersCleared`、`cleared`、`finalScore`、`regulation`、`baseScore`（倍率の前の点）、`absoluteMult`（ABSOLUTE のときだけ） |

- **なぜゲーム内の倍率を使わないか**：ゲーム内の倍率は Red で 3.0、ABSOLUTE は 4 つの設定の掛け算（敵 HP × 敵ダメ ÷ 自 HP × 自ダメ、各 0.1〜5.0）で、理屈の上で最大 **2,500 倍** になる。そのまま総合に入れると Tactics だけで総合が決まるので、総合には共通基盤の係数で入れる（ゲーム内のランキングの倍率はそのまま）
- **v1 の成績から計算し直す**：v1 で保存した生の成績には倍率の前の点がないので、最終スコア ÷ ゲーム内の倍率（Common 1.0 ／ Egg 1.2 ／ Baby 1.5 ／ Blue 2.0 ／ Red 3.0）で戻す。ABSOLUTE は倍率が分からないので節目の点だけにする（2026-10-17 の本番の成績は Common・第 4 章で敗北の 1 件だけで、点は変わらない）
- 計算式：`platform/scoring/tactics.v2.js`（v1 は記録として残す）

### 3.2 Survivor（1 プレイ ＝ 1 回の挑戦）

計算式 v2（2026-10-17）。

| | 中身 |
|---|---|
| 節目の点 | ステージ 1 クリア 1,000 ／ ステージ 2 クリア 3,000 ／ 全 3 ステージクリア 5,000 |
| 成績の点 | 全クリアのとき：活動レポートのスコア（倍率の前）× レギュレーション倍率（**上限 2.0**）× **1/30** |
| 係数の根拠 | ふつうのクリアの活動レポートのスコアを **150,000** と見た。実測で確かめた（下） |
| 倍率の上限 | ABSOLUTE の倍率は 4 軸の平均で最大 ×5.0。出現数の軸で撃破数（スコアの大半）も増えるので、倍率は 2.0 で止める（作者の決定 2026-10-17。Tactics v2 の ABSOLUTE の上限と同じ考え方）。2.0 未満はそのまま掛ける |
| 例 | ステージ 1 を終える 1,000 ／ ふつうに全クリア（150,000）10,000 ／ ABSOLUTE ×2.0 で 150,000 なら 15,000（×5.0 でも 15,000）／ 撃破を伸ばして 300,000 なら 15,000 |
| 送る成績 | `stagesCleared`、`cleared`、`reportScore`、`regulationMul`（ほかに `regulation`・`absolute`。点には効かない） |
| v1 からの移り変わり | 係数は同じで、倍率の上限だけが増えた。v1 の生の成績からそのまま計算し直せる（本番の記録は 2026-10-17 時点で 0 件） |

**実測（2026-10-17）**：活動レポートのスコア ＝ 撃破 × 100 ＋ 最高 Lv × 500 ＋ 取ったエクステンションの種類 × 300 ＋ max(0, 60,000 − IGT 秒 × 50) ＋ 5,000。

- 本物のゲーム（v1.0.0）をヘッドレスの Chromium で動かし、時計を早回しして、自動プレイ（楕円に回って敵を引き連れ、近くの宝石を拾う。レベルアップでは持っている物の強化を優先）で NORMAL を 10 体 × 2 回走らせた（結果が出たのは 18 回）
- ボットがうまく動いた回（武器が当たり、宝石を拾えた回）の全クリアは **147,663〜162,500**（5 回。撃破 1,144〜1,311・最高 Lv 15〜17・種類 10〜13・IGT 13 分 54 秒〜15 分）。撃破 × 100 が 7〜8 割を占める
- 本番の RTA の記録 1 件（作者・IGT 12 分 46 秒）に当てはめると、ボスを早く倒した分だけ撃破は減り（約 1,050）、時間の点は増える（約 21,700）ので、約 144,000
- どちらも 150,000 の ±1 割に入るので、係数 1/30 は直さない。ボットがうまく動かなかった回（周回する武器が敵に届かない・宝石を拾えずに Lv 1 のまま）は、ふつうのクリアとは見なさなかった
- 撃破できる数の上限は、出現の間隔で決まる（ステージ 1〜3 で 0.8 / 0.68 / 0.56 秒に 1 体。5 分耐久でも約 1,350 体）。NORMAL では 150,000 から大きく外れない

### 3.3 Fortress（積み上げ ＝ レベルごとの自己ベストの合計。v2）

| | 中身 |
|---|---|
| 点 | **レベルごとの自己ベストの合計**。レベルの点 ＝ 節目の点 ＋ 成績の点 |
| 節目の点 | クリアしたレベルの重み w：レベル 01 ＝ 500、レベル 02〜09 ＝ 562.5（9 レベルで 5,000）。L1〜Ln をクリアしたときの節目の合計は、v1 の「レベル n をクリア」と同じ |
| 成績の点 | w × （残り体力の割合 ＋ 空きスロットの割合）÷ **1.2** ＋ 早呼びのボーナス GUM × **1** |
| 残り体力の割合 | クリアしたときの体力 ÷ 最大体力 |
| 空きスロットの割合 | （そのレベルのスロット数 − 置いたヒーローの数）÷ スロット数。**少ないヒーローでクリアするほど高い**（縛りの度合い） |
| 早呼びのボーナス | そのクリアで、Wave を繰り上げて呼んだときにもらったボーナス GUM の合計（敵を多く残して呼ぶほど・スキルツリーの「神託の軍馬」で増える）。**伸び続ける成績**（作者の決定 2026-10-17）。上限なし |
| 係数の根拠 | ふつうのクリアを「体力 3 分の 2 が残る・15 スロットに 7 体・早呼びなし」と見た（2/3 + 8/15 ≒ 1.2 → 成績の点 ＝ w）。早呼びの係数は、スキルツリー最大のボットで全 9 レベルの早呼びボーナスが約 2,200 GUM（1 レベル 60〜860）だったので、1 GUM ＝ 1 点（上振れが 1〜2 割）にした |
| 自己ベスト | レベルごとに、点の一番高いクリアの成績。スキルツリーの積み上げで同じレベルを良い成績でクリアし直せば、そのレベルの点が上がる（積み上げは点に効いてよい。DeckBattle の永続強化と同じ） |
| 例 | レベル 01 をふつうにクリア 1,000 ／ 全レベルをふつうにクリア 10,000 ／ 全レベルを体力を減らさず 4 体・早呼び 2,200 GUM でクリア 約 14,400 |
| 送る成績 | `levels`：{ `L1`〜`L9`：{ `hpLeft`、`maxHp`、`heroesUsed`、`slots`、`earlyBonus` } }（セーブにあるレベルごとの自己ベスト。クリアしたレベルだけ） |

- **種類は `progress`**（積み上げ）。ゲームはクリアで自己ベストが変わったとき、セーブにあるレベルごとの自己ベストをまとめて送る
- **共通基盤が前回の自己ベストと束ねる**：計算式に `combine`（成績をいくつも束ねて、レベルごとに点の一番高い成績を残す純関数）を持たせ、API は「前回の自己ベストのもとの成績 ＋ 今回」を束ねてから計算・保存する。別の端末・古いセーブ・v1 のころのクリア（セーブに成績が残っていない）から送っても下がらない
- **v1 からの移行**：v1 の生の成績（1 レベルずつ）も `combine` で束ねられる。毎日の掃除（計算し直し）で、v1 の自己ベストを持つ人は保存してある生の成績ぜんぶを束ねて v2 で計算し直し、束ねた成績 1 つを自己ベストのもととして保存し直す（もとの生の成績は消す）。v1 の公開（2026-10-16）から 90 日以内なので、生の成績は消えていない
- 仮アカウントを本アカウントにまとめるときも、両方の成績を束ね直す（高いほうを残すだけだと、片方でだけクリアしたレベルが消える）
- v1 の形の成績（`levelId`、`won`、…）も受け付ける（読み込み直していない古いゲームから送られても足し上がる）

### 3.4 DeckBattle（積み上げ ＝ ストーリーの進み具合）

| | 中身 |
|---|---|
| 節目の点 | 本編のノード（13 個）を k 個制覇で 1,000 + (k − 1) × 333（最初のノード 1,000 〜 時空のはざま 5,000）。特別ステージ（3 ノード）は 1 つ制覇するごとに + 1,667 |
| 成績の点 | 制覇したノードごとの自己ベストの合計。ノードの成績 ＝ **戦力** ＋ **4,800 ÷ 平均の戦闘時間（秒）** |
| 戦力（新設） | ノードの最後のステージをクリアしたときのパーティ（6 枠）の合計。1 体 ＝ レアリティの基礎値（Common 10 〜 Legendary 22。`RARITY.budget`）× Lv の倍率（`LEVEL_MULT`）× （1 ＋ 永続強化 `permMult`）。**強いほど高い** |
| 平均の戦闘時間 | そのノードで戦った戦闘の、ゲーム内の秒数の平均（`run.history[].time`）。短いほど高い |
| 係数の根拠 | ふつうのクリア（本編の 13 ノード）を「戦力 約 180・1 戦 約 30 秒」と見た（180 + 160 ＝ 340 点 × 13 ノード ≒ 4,400 → 合計 約 9,400）。特別ステージはその上乗せ |
| 送る成績 | `clearedStages`（制覇したステージの一覧）、`nodes`（ノードごとの最高の `power` と最短の `avgBattleSec`） |

## 4. しくみ

- **送る**：SDK の `submitScore({ metrics })`。1 回の挑戦で終わるタイトルは、終わったとき（クリアでも負けでも）に送る。積み上げのタイトルは、進み具合が増えたとき（ノードの制覇・カードが増えたとき。多くても 1 分に 1 回）に送る
- **計算**：サーバー（このリポジトリ）の `platform/scoring/<タイトル>.v1.js`。純関数にして、基準プレイ A・B が目安の点になることをテストに書く
- **保存**：生の成績（`plays`）と、タイトルごとの自己ベスト（`title_scores`）。係数を変えたら版を上げ、保存した生の成績から全員を計算し直す（SPEC-001 8.4）
- **受け付け**：そのタイトルのサブドメインからだけ。成績はゲームが自分で申告する値なので、タイトルごとに「ありえない値」の範囲だけ確かめる（Workshop の今のランキングと同じ考え方）。上限は設けないが、ありえない値ははじく
- **未ログイン**：トロフィー・RTA と同じく仮アカウントに貯め、ログインでまとめて登録（D6）
- **画面**：bearko.games に総合ランキング（合計点・タイトルごとの内訳）、マイページに自分の内訳と「次の節目まであと何点」
- **進め方**：係数が決まったタイトルから順に（まずトロフィー・RTA を入れた Survivor・Tactics・Fortress・DeckBattle）。各ゲームの組み込みは、そのリポジトリの SPEC で

## 5. 決まったこと（作者の決定 2026-10-16）

1. 暫定の基準（3 章の太字）で実装を進める
2. Fortress は残り体力と使ったヒーローの少なさ、DeckBattle はクリア時間と最終的なパーティの強さ（戦力を新設。強いほど高い）で測る
3. 難易度で係数を変える（まず 10 buy year）
4. TCG は保留。Factory は Lv 5 までの時間・工房 Lv（設備）・クエスト攻略数・クラフトの数と内訳で測る

## 6. これから（バックログ）

- **難易度ごとのレギュレーション**：ゆくゆくは全タイトルに難易度の調整を入れ、総合スコアのランキングを難易度ごとに分けられるようにする（作者の方針 2026-10-16）。そのときは、スコアの記録に難易度を持たせておく（今から `metrics` に入れて送る）
- TCG：連戦とクリアの概念（MyCryptoTCG#5）ができたら入れる
- 係数の見直し：公開後、タイトルごとの点数の分布を見て直す

### 6.1 同じ条件で競うレギュレーション（案：10 buy year の週替わりチャレンジ。未実装）

10 buy year の週替わりチャレンジは、週ごとに決まるシード（`weeklySeed`）で、誰が遊んでも同じ相場・同じ出来事から始まる。難易度はふつうに固定で、継承・キャリアの型・師匠はない。いまはゲーム自身の API（`/api/ranking`、Cloudflare の Worker）が、週ごとの純資産のランキングを持っている。これを共通基盤の「同じ条件で競う」レギュレーションにする案。

| | 案 |
|---|---|
| 何で競うか | ゲーム内の成績そのまま（10 buy year は純資産）。総合スコアの点ではない（同じ条件なので、係数で合わせる必要がない） |
| 期間 | レギュレーションごとに「回」を持つ（10 buy year は ISO 週 `2026-W42`。日本時間の月曜 0 時に切り替わる）。登録は今回と前回だけ受け付ける（週をまたいで遊び終えた人のため。いまのゲームと同じ） |
| 定義 | `platform/scoring/` か新しい `platform/regulations.js` に、`{ id: '10buy-weekly', game: '10buy', metric: 'netWorth', order: 'desc', round: 'isoWeek', match: { difficulty: 'normal', legacy: null, mentor: false } }` のように書く。`match` に合わない成績は、そのレギュレーションには入れない（総合スコアには、ふつうに入る） |
| 送り方 | **ゲームと SDK は変えない**。いまの `submitScore` の `metrics.weekly`（週）で、どの回の挑戦かが分かる |
| 保存 | **表は足さない**。生の成績（`plays`）に `metrics` がそのまま残っているので、`json_extract(metrics, '$.weekly')` で回ごとに引ける。ただし `plays` は自己ベストのもとでないと 90 日で消えるので、回ごとのランキングも 90 日で見えなくなる（いまのゲームと同じ）。人が増えて遅くなったら、索引か表を足す（そのときはマイグレーション） |
| API | `GET /api/score/regulation?id=10buy-weekly&round=2026-W42` で、その回のランキング（1 人 1 件・自己ベスト・上位 100 人。ログインした人だけ）。`GET /api/score/regulations` で定義の一覧 |
| 画面 | ポータルの総合ランキングに「週替わり」のタブを足す。ゲームのタイトル画面からも、その週のランキングへのリンクを出す |
| ゲームの今のランキング | しばらく並べて動かす。共通基盤の方がそろったら、ゲームの `/api/ranking` を止めて、ゲームの画面は共通基盤のランキングを読む（名前の登録は共通ログインの表示名になる） |

- 決まっていないこと（作者の確認が要る）：① ゲームのランキングを共通基盤に移すか、並べて残すか ② 未ログインの人の記録を出すか（いまのゲームは名前を入れれば誰でも載る。共通基盤のランキングはログインした人だけ） ③ デイリーチャレンジ（日替わり。いまはその端末だけの記録）も同じ形で入れるか
- 難易度ごとのレギュレーション（6 章）も、`match: { difficulty }` と「回なし」で同じ形に書ける。継承ありの周の別枠（3.8）も `match: { legacy }` で書ける
