# SPEC-001 bearko.games 共通基盤（共通ログイン・総合スコア・RTA・トロフィー）

| 項目 | 内容 |
|---|---|
| 状態 | Accepted（2026-10-16） |
| 作成 | 2026-10-15 |
| 対象 | bearko.games 配下の全タイトル（下表の 9 作品）と、ポータル `bearko.games` |
| 置き場所 | 共通基盤のサーバー処理・クライアントスクリプト・ポータル画面は、このリポジトリ（bearko.games の Worker）に置く |

## 1. 目的

bearko.games 配下のゲームを「ひとつのシリーズ」として遊べるようにする。

- **共通ログイン**：1 回の Google ログインで、全タイトルのランキング・トロフィーに参加できる
- **総合スコア**：各タイトルの成績をスコアにし、合計で競う総合ランキングを作る
- **RTA モード**：タイトルをまたいだクリアタイムを計測する（例：全 9 ゲームのステージ 1 クリアの合計タイム）
- **トロフィー（称号）**：タイトルごとのものと、タイトルをまたぐものを作る

## 3. 全体構成

```
 プレイヤーのブラウザ
 ├─ tactics.bearko.games など各ゲーム
 │    └─ <script src="https://bearko.games/sdk/v1.js">  … window.BearkoGames
 │         │  fetch(credentials: "include")
 │         ▼
 └─ bearko.games（このリポジトリの Worker）
      ├─ /            ポータル（作品一覧・総合ランキング・RTA・トロフィー）
      ├─ /login       Google ログイン画面（ポップアップで開く）
      ├─ /sdk/v1.js   ゲームが読み込むクライアントスクリプト
      └─ /api/*       共通基盤の API ── D1 データベース「bearko-platform」
```

- サーバー処理はすべて bearko.games の 1 つの Worker に集める。各ゲームは **スクリプト 1 本を読み込み、決まった関数を呼ぶだけ** にする
- 各ゲームの既存のランキング（Workshop・10 buy year の Upstash、Tactics などの GAS）は当面そのまま残す。共通基盤は「総合」と「横断」を受け持つ
- 費用：Cloudflare の無料枠（Workers・D1）に収まる見込み

## 4. 共通ログイン

### 4.1 しくみ

1. ゲームで「ランキングに登録」「トロフィー獲得」などの場面になったら、SDK が `https://bearko.games/login` をポップアップで開く（ポップアップが使えない環境では、そのページへ移動して戻ってくる）
2. `/login` で Google Identity Services のボタンを出し、受け取った ID トークンをサーバーで検証する
3. サーバーはセッションを作り、Cookie `bg_session` を発行する
   - `Domain=.bearko.games; Path=/; HttpOnly; Secure; SameSite=Lax`
   - これで、どのサブドメインのゲームからでも同じログイン状態になる（サブドメイン同士は「同じサイト」なので Lax でも送られる）
4. ポップアップは `postMessage` でゲームにログイン完了を知らせて閉じる

### 4.2 API の受け入れ先

- `/api/*` は CORS で `https://*.bearko.games` と `https://bearko.games` だけを許可し、`Access-Control-Allow-Credentials: true` を返す
- 書き込み系（POST）は Origin を確かめ、許可していない Origin からは受け付けない（CSRF 対策）

### 4.3 Google の設定

- OAuth クライアントは **Workshop で使っているものを使い回す**（クライアント ID `757389530825-7kee3d573nk0b03iv9mc0qeq8952kf5n.apps.googleusercontent.com`。公開してよい値）。同じクライアントなら Google のアカウント識別子（`sub`）が確実に一致し、Workshop の既存プレイヤーの紐付けを引き継げる
- 「承認済みの JavaScript 生成元」に `https://bearko.games` を追加する（ログイン画面は bearko.games にだけ置くので、各サブドメインの追加はいらない）

### 4.4 保存する個人情報

- 保存するのは Google の `sub` と、プレイヤーが決める **表示名** だけ。メールアドレス・本名・顔写真は保存しない
- 退会（全記録の削除）をポータルから自分でできるようにする

### 4.5 Workshop の記録の引き継ぎ

- Workshop は、Google の `sub` → Workshop のプレイヤー ID の対応を Upstash に持っている（`lb:google:<sub>`）
- 共通基盤も同じ OAuth クライアントを使うので、**ログインした人の `sub` で Workshop のプレイヤー ID を引ける**。記録を移しかえる必要はなく、「このアカウントの Workshop の記録はこれ」と結びつけるだけでよい
- Workshop の共通ログインへの切り替え（段階 1）のときに、この結びつけを入れる

### 4.6 仮アカウント（未ログイン中の記録）

- 未ログインの人が初めてトロフィーを獲得する・RTA を始める・スコアを送るときに、サーバーが **仮アカウント** を作り、Cookie `bg_guest`（`Domain=.bearko.games; HttpOnly; Secure; SameSite=Lax`、有効 90 日）を発行する。ページを開いただけでは作らない（データを増やさないため）
- 仮アカウントの記録は、**サーバーの時刻で記録する**。クリアタイムも、ログイン後と同じ方法で測るので、あとからまとめて登録しても公式記録として扱える
- ログインすると、その端末の仮アカウントの記録を本アカウントに **まとめて移す**（同じトロフィーは 1 つにまとめ、スコアは自己ベストを残す）
- 仮アカウントの記録はランキングには出さない。ポータルとゲーム内に「未登録のトロフィー n 個・記録 n 件」と表示し、ログインを勧める
- 最後に使ってから 90 日たった仮アカウントは、記録ごと消す
- 注意：仮アカウントはブラウザごと。Cookie を消す・別の端末で遊ぶと、貯めた記録は引き継げない（ポータルとログインの案内に書いておく）

## 5. クライアント SDK（各ゲームが使うもの）

`https://bearko.games/sdk/v1.js` を読み込むと `window.BearkoGames` が使える。

| 関数 | 用途 |
|---|---|
| `init({ game: "tactics", version: "1.2.0" })` | 最初に 1 回呼ぶ |
| `getUser()` | ログイン中なら `{ id, name }`、していなければ `null` |
| `login()` | ログイン画面を開く。終わると `Promise` が解決する |
| `submitScore({ regulation, metrics })` | 1 プレイの成績を送る（`metrics` は生の成績。スコアの計算はサーバー側） |
| `unlockTrophy(id)` | トロフィーの獲得を送る |
| `rta.start({ regulation })` / `rta.checkpoint(id, { igtMs })` / `rta.abort()` | RTA の計測（6.6）。最後のチェックポイントを送ると、その計測は終わる |

守ること：

- **SDK が読み込めない・通信に失敗しても、ゲームは最後まで遊べる**こと（すべての関数は失敗しても例外を投げず、結果を `{ ok: false }` で返す）
- 未ログインで `unlockTrophy` / `rta.*` / `submitScore` を呼ぶと、**仮アカウント**（4.6）に貯める。ログインを促す表示は SDK が出す（何個貯まっているかを見せる）
- ゲーム側のコードは Cookie や localStorage に触らない（ログイン状態は SDK と bearko.games が持つ）。Tactics の憲章とも矛盾しない

## 6. RTA モード

### 6.1 区切り（チェックポイント）

各タイトルは「どこで区切れるか」を **チェックポイント** として登録する。

| 種類 | 意味 | 例 |
|---|---|---|
| `stage` | ステージ・章・レベルのクリア | Tactics 第 1 章クリア、Fortress レベル 1 クリア |
| `milestone` | ゲーム内で定めた節目 | Workshop 30 日目、10 buy year 昇進、Factory 1 年目終了 |
| `clear` | ゲームクリア | Tactics 全章クリア、Survivor 全ステージクリア |

チェックポイントは `{ game, id, kind, order, label }` で共通基盤に登録する。ゲームのアップデートで区切りが変わったときは、新しい id を足し、古いものは「廃止」にする（過去の記録は消さない）。

### 6.2 レギュレーション

レギュレーションは「どのタイトルの、どこからどこまでを、何本足すか」の組み合わせで定義する。

```js
{
  id: "all9-stage1",
  name: "全 9 ゲーム ステージ 1 合計",
  segments: [
    { game: "tactics",    to: "ch1-clear" },
    { game: "fortress",   to: "level01-clear" },
    // … 対応しているタイトルの分
  ],
  order: "any",        // "any"：タイトルを好きな順に遊べる ／ "fixed"：決めた順に
}
```

- 1 タイトルだけのもの（例：Tactics 全章クリア）も、複数タイトルのものも、同じ形で書ける
- 区切りが用意できていないタイトルは、そのタイトルに区切りができてからレギュレーションに加える（7 章）

### 6.3 時間の測り方

- **公式タイムは、サーバーが受け取った時刻の差**で決める（ブラウザが送るタイムは信用しない）
  - `rta.start` でサーバーが計測 ID と開始時刻を発行する。チェックポイントごとにサーバーの受信時刻を記録する
- ゲーム内時間（IGT）もあわせて送って保存する（参考値。将来「IGT 部門」を作れるように）
- 複数タイトルのレギュレーションでは、**各区間のタイムの合計**を公式タイムにする（タイトル間の移動・読み込みの時間は数えない）
- 未ログインでも計測できる（仮アカウントにサーバーの時刻で記録し、ログインしたときに本アカウントへ移す。4.6）

### 6.4 無操作の扱い（参考記録）

- 計測の開始から終了までのあいだに、**15 分以上操作がなかったら、その記録は参考記録** にする（D8）。タイトル間の移動中も含めて数える
- 参考記録はランキングには出さない。マイページの個人記録には「参考記録」と表示して残す
- 判定のしかた
  - SDK は、ゲームの画面で操作（タップ・クリック・キー入力）があった時刻を覚える
  - 計測中は、操作があったときだけ **5 分に 1 回まで** サーバーに「操作あり」を送る。チェックポイントの送信も「操作あり」として数える
  - 各送信には「ここまでで一番長かった無操作の時間」をつけ、これが 15 分以上なら参考記録にする
  - あわせてサーバーでも、「操作あり」を受け取った間隔が **20 分**（15 分＋送信の間隔 5 分）を超えたら参考記録にする（ブラウザが止まっていた場合など）
- 「操作あり」の送信は、行を増やさず計測の行（`rta_runs`）の最終操作時刻を書き換えるだけにする（データ量を増やさない）

### 6.5 不正への備え

- 区間ごとに「これより速いのはありえない」最短時間を決め、下回る記録ははじく（Workshop の `MIN_CLEAR_SECONDS` と同じ考え方）
- 管理者は記録の削除・プレイヤーの締め出しができる（Workshop の管理トークンと同じ方式）

### 6.6 API と SDK（段階 4 で作るもの）

チェックポイントとレギュレーションの定義は、トロフィーと同じくコード（`platform/rta.js`）に置く（表 `checkpoints`・`regulations` は作らない。変えるときは PR で）。

| API | 用途 |
|---|---|
| `GET /api/rta/regulations` | レギュレーションとチェックポイントの定義 |
| `POST /api/rta/start { regulation }` | 計測を始める。サーバーが計測 ID と開始時刻を決める。同じ人の、終わっていない計測は「中断」にする（同時に走れるのは 1 本） |
| `POST /api/rta/checkpoint { runId, checkpoint, igtMs, idleMs }` | 区切りの通過。**決めた順番どおり**でないものは受けない。最後の区切りなら計測を終え、公式タイム・参考記録かどうか・自己ベストか・順位を返す |
| `POST /api/rta/ping { runId, idleMs }` | 「操作あり」（6.4）。計測の行の最終操作時刻を書き換えるだけ |
| `POST /api/rta/abort { runId }` | 中断（ゲームオーバー・タイトルに戻ったとき） |
| `GET /api/rta/ranking?regulation=…` | ランキング（1 人 1 件・自己ベスト・上位 100 人）。**ログインした人の、参考記録でない記録だけ** |
| `GET /api/me/rta` | 自分の記録（参考記録も含む。未ログインなら仮アカウントの分） |

- 計測を始める・区切りを送るのは、レギュレーションの **そのタイトルのサブドメインから** だけ受ける（トロフィーと同じ）
- 区切りごとの最短時間（6.5）を下回ったら、その計測は「無効」にして、ランキングにも個人記録にも出さない
- 未ログインで走った記録は仮アカウントに入り、ログインしたときに本アカウントへ移る（移ったあとはランキングに出る）
- SDK は計測中、画面の上に **経過時間（目安）** を出す。区切りでは区間タイム、終わったら公式タイムを通知で出す。未ログインなら「ログインしてランキングに登録」を添える
- 掃除：始めてから 2 日たっても終わっていない計測と、中断・無効の計測は、毎日の掃除で消す

### 6.7 最初のレギュレーション：Survivor 全 3 ステージ（`survivor-normal`）

| 区切り（`order` 順） | 種類 | 最短時間（6.5） |
|---|---|---|
| `stage1` ステージ 1 クリア | `stage` | 3 分 55 秒 |
| `stage2` ステージ 2 クリア | `stage` | 7 分 50 秒 |
| `clear` 全 3 ステージクリア | `clear` | 11 分 45 秒 |

- ルールは NORMAL（難易度の調整なし）。ヒーローは自由
- 計測の開始は、ヒーローを選んで **ステージ 1 が始まったとき**。ステージの合間の画面・レベルアップの選択の時間も含める（実時間）
- 最短時間の根拠：各ステージは、ゲーム内の時間で 4 分にボスが出て、倒すか 5 分たつと終わる。ゲーム内の時間は実時間より速く進まない（1 コマ 0.05 秒まで）ので、ステージ 1 は 4 分より速く終われない。通信の遅れの分、5 秒ずつ短くしている
- IGT は、各ステージのゲーム内の経過時間の合計

### 6.8 Workshop 黄金のエクステンション（`workshop-golden`）

| 区切り（`order` 順） | 種類 | 最短時間（6.5） |
|---|---|---|
| `epic` Epic 解放（インペリアル製法の習得） | `stage` | 20 分 |
| `legendary` Legendary 解放（MCH製法の習得） | `stage` | 30 分 |
| `clear` 黄金のエクステンション | `clear` | 50 分 |

- ルールは 1 周目（リセット直後・ランド移転の引き継ぎなし）。ゲームのホームの「RTA で始める」でセーブを消し、**Day 1 の「開店する」** で計測を始める。スキルツリー・結果画面・メニューの時間も含める（実時間）
- 区切りはスキルツリーの前提で、この順番でしか取れない
- 最短時間の根拠：ゲームの自動プレイの active（3 タップ/秒・オーバークロック・魔石・選択イベントあり）が、営業時間で 57.5 / 85.8 / 140.4 分（Workshop の `npm run balance -- 300 42`、2026-10-17）。営業日の長さは固定で早送りがないので、実時間は営業時間より短くならない。人が自動プレイの約 3 倍速く進むことはないと見て、その約 35% にした
- IGT は営業時間（Workshop のランキング「最速クリア」と同じ。スキルツリーやメニューを開いている間は数えない）
- 2.5 時間ほどかかり、再読み込みすると SDK の計測が消える（記録にならない）。15 分の無操作で参考記録になるのは、ほかのレギュレーションと同じ
- 詳しくは Workshop の docs/ROADMAP.md 8.4

### 6.9 Factory 工房 Lv.5（`factory-lv5`）

| 区切り（`order` 順） | 種類 | 最短時間（6.5） |
|---|---|---|
| `lv2` 工房 Lv.2 | `milestone` | 4 秒 |
| `lv3` 工房 Lv.3 | `milestone` | 6 秒 |
| `lv4` 工房 Lv.4 | `milestone` | 10 秒 |
| `clear` 工房 Lv.5（クリア） | `clear` | 15 秒 |

- ルールは「はじめから」（セーブなし）。タイトルの「RTA で始める」で、**2018 年 12 月 1 週の開始**から計測を始める。期限（8 年 = ゲーム内 384 週）を過ぎたら計測をやめる（`abort`）。メニューやお知らせで時間が止まっている間も含める（実時間）
- 工房 Lv は 1 つずつしか上がらないので、区切りはこの順番でしか取れない
- 速さは設定の 2 倍速（1 週 3.5 秒）まで。テスト用の 20 倍速は `?debug=1` のときだけで、そのときは「RTA で始める」を出さない
- 最短時間の根拠（**理屈の下限で、暫定**）：Lv.2 にはクラフト 1 個と出品 1 件（最短 1 週 = 7 コマ）、Lv.3・4・5 にはクラフト 5・15・30 個が要る。並行は Lv.1 で 1・Lv.2 で 2・Lv.3 から 3 つ。クラフト 1 個は、短縮をすべて重ねても 2 コマ以上かかる（Common の 12 週を 3 倍速 → 4 週 = 28 コマ、人数 1.4 倍 × 潤滑油 2 倍で 3.3 コマ。余裕を見て 2 コマ）。2 倍速の 1 コマ 0.5 秒で数えると 4.5 / 6.5 / 10.5 / 15.5 秒になり、そこから切り捨てた。ふつうは 3 年（156 週）ほどかかり、2 倍速でも 9 分を超える。作者の通しプレイの記録が出たら引き上げる
- IGT はゲーム内の経過（1 週 = 7 秒で数える）
- 再読み込みすると SDK の計測が消える（セーブから続けても計測は続かない）。15 分の無操作で参考記録になるのは、ほかのレギュレーションと同じ
- 詳しくは Factory の docs/specs/SPEC-003-platform-rta.md

## 8. 総合スコア

### 8.1 考え方

- 各タイトルは、1 プレイの **生の成績**（`metrics`。例：純資産、撃破数、クリアタイム）を送る
- 共通基盤は、タイトルごとの **計算式** で生の成績を **タイトルスコア** に変える
- **総合スコア ＝ 各タイトルの自己ベストのタイトルスコアの合計**

### 8.2 計算式のルール

**同じプレイ内容なら、誰が・何回目に遊んでも・他の人がどうであっても、同じ点になる** こと。

- 計算式に入れてよいのは、**そのプレイの成績だけ**（例：純資産、撃破数、クリアした章、ターン数、クリアタイム）
- **入れないもの**
  - 初回クリア・アカウントごとに 1 回だけの上乗せ（サブアカウントで稼ぐのが最適解になるため）
  - 順位・上位何 % といった、他のプレイヤーの成績に左右されるもの（自分の腕で上がった実感が持てないため。タイトル単体では順位も変わらない）
- 「クリアしたプレイかどうか」で点を変えるのはよい（どのプレイでも同じ条件で付くため）

### 8.3 「おおよそ公平」の合わせ方

「同じくらい遊んだ人は、どのタイトルでも同じくらいの点になる」ように、作者が **基準プレイ** を決めて合わせる。

- タイトルごとに、成績で書いた **基準プレイ** を 2 つ決める
  - **基準 A（ひととおり遊んだ）≒ 1,000 点**（例：Tactics なら第 1 章をクリアしたプレイ）
  - **基準 B（ふつうに遊んでクリアした）≒ 10,000 点**（例：Tactics なら全章をふつうのターン数でクリアしたプレイ）。上限ではなく **目安**
- **上限は設けない**（D11）。イベントの上振れや研究でハイスコアが更新され続けるようにする。計算式で頭打ち・段差を作らない（成績の部分は、ゲーム内の成績に係数を掛けるだけ）
- 1 本だけ点が飛び抜けるようなら、上限ではなく **係数の見直し** で合わせる（8.4）
- 計算式は、基準 A・B が目安の点になるように係数を決める。基準プレイはタイトルの計算式と一緒にテストに書く
- 点数の分布（中央値など）は、作者が見直しの **参考に見るだけ** で、計算式には入れない

### 8.4 計算式の管理と見直し

- 計算式はこのリポジトリに **バージョン付きの純関数** として置き、テストを書く（例：`platform/scoring/tactics.v1.js`）
- **生の成績を必ず保存する**。計算式を直したら、保存してある生の成績から **全員のスコアを計算し直す**（過去の記録も新しい式で並ぶ）
- 見直しのきっかけ：ゲームのバランス調整で、基準プレイの成績の出方が変わったとき
- ポータルの管理画面で、タイトルごとの点数分布を見られるようにする（見直しの判断材料）
- 計算式を変えたら、ポータルに「スコア計算の更新」として告知する

## 9. トロフィー

### 9.1 種類

| 種類 | 例 | 判定する場所 |
|---|---|---|
| タイトル内 | Tactics 第 1 章クリア、Fortress 全レベルクリア | ゲームが `unlockTrophy(id)` を送る |
| タイトル横断 | 2 タイトルでトロフィー獲得、対応タイトルすべてでクリア | 共通基盤が獲得状況から判定する（ゲームからは送れない） |

### 9.2 定義

- トロフィーの定義は、このリポジトリの `platform/trophies.js` に置く（ID・タイトル・名前・説明・クリアのトロフィーかどうか）
- タイトル内のトロフィーは、**そのゲームのサブドメインからしか獲得を受け付けない**（例：`tactics.*` は `tactics.bearko.games` から）。知らない ID ははじく
- 名前・説明はあとから変えてよい。ID は変えない（変えると獲得記録とつながらなくなる）
- 横断トロフィーは、一度獲得したら、対応タイトルが増えて条件が厳しくなっても消えない

### 9.3 しくみ

- `unlockTrophy(id)`：ログイン中は本アカウント、未ログインなら仮アカウントに記録する（仮アカウントがなければ、このとき作る）。同じトロフィーを何度送っても 1 つ
- 獲得すると、SDK が画面の下に小さく通知を出す。未ログインなら「未登録のトロフィー n 個 — ログインして登録」を添える。通知を出したくないゲームは `init({ ui: false })` で消せる
- ログインすると、仮アカウントのトロフィーをまとめて本アカウントに移し、横断トロフィーを判定し直す
- マイページで、タイトルごとの獲得状況を見られる

## 11. データ量と費用の見積もり（1 日 1 万人が遊ぶ場合）

前提（1 人・1 日あたり）：2 タイトルを遊ぶ、ログイン確認 2 回、スコア送信 2 回、トロフィー獲得 2 個、RTA は 10 人に 1 人が 1 回（区切り 5 つ）。

| 項目 | 1 日あたり | 無料プランの上限 | 有料プラン（月 $5）に含まれる量 |
|---|---|---|---|
| Worker の呼び出し（API） | 約 7 万回 | 10 万回／日（**アカウント全体**） | 1,000 万回／月（≒ 33 万回／日） |
| D1 の書き込み行数 | 約 14 万行（索引込み） | 10 万行／日 | 5,000 万行／月 |
| D1 の読み出し行数 | 約 100 万行（ランキング表示が主） | 500 万行／日 | 250 億行／月 |
| D1 の保存量の増え方 | 約 17 MB／日（≒ 500 MB／月） | 5 GB | 5 GB（超えた分は 1 GB あたり月 $0.20） |

- **1 日 1 万人なら、Workers の有料プラン（月 $5）が要る**。無料プランでは、API の呼び出しが他のゲームの API（Workshop・10 buy year）と合わせて上限に近づき、D1 の書き込みは上限を超える
- 1 日数千人までなら、無料プランに収まる見込み
- 保存量は、そのまま貯めると 10 か月ほどで 5 GB に届く。そこで次のように整理し、**1〜2 GB 前後で横ばい** にする
  - 生の成績（`plays`）：自己ベストのもとになったものは残し、それ以外は 90 日で消す
  - 仮アカウント：最後に使ってから 90 日で消す
  - 期限切れのセッション：毎日消す
- 静的ファイル（ゲーム本体・SDK・ポータル）の配信は、どのプランでも無料・無制限
- 見積もりは前提しだいで変わる。Cloudflare のダッシュボードで実際の量を見て、上限の 7 割を超えたら見直す
